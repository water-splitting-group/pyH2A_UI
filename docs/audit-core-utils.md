# CORE — Static review of the pyH2A core data layer

Scope: `Utilities/input_modification.py`, `Utilities/IO/{input_resolver,output_inserter}.py`, `Utilities/check_functions.py`, `Utilities/constants.py`, `Discounted_Cash_Flow.py`, `Utilities/{find_nearest,docstring_generation,plugin_input_output_processing,functional_unit}.py`. Read-only; no code executed. Line numbers verified against the local clone at master.

Headline: the markdown parser is not a markdown parser — it is a 35-line state machine that silently produces an *empty or mis-columned* dict for several inputs that are perfectly valid GitHub-flavoured markdown (CORE-1, CORE-2). Path resolution converts four distinct user mistakes into the same `setting to 1` warning and keeps going (CORE-8, CORE-9), so wrong numbers reach the levelized cost without an exception. And `dcf.inp` is mutated in place with no copy on entry (CORE-14), so a UI that re-runs the engine on the same dict gets a different (and eventually crashing) answer the second time. Those four are the ones a UI must design around.

## Detailed findings

### CORE-1 — Leading/trailing pipes produce a silently empty table
**BUG-confirmed-by-reading** · `pyH2A/src/pyH2A/Utilities/input_modification.py:262-275` · known upstream? **NEW**

The parser recognises the header separator only by `if line[0] == '-'` (line 266). GitHub-flavoured markdown very commonly writes tables with a leading pipe (`| Name | Value |` / `| --- | --- |`), which every markdown formatter (prettier, most editors, most LLM output) will produce. For such a file `line[0]` is `'|'`, so `table` is never set to `True`, no data row is ever stored, and the separator line itself is captured as `header_entries` (line 270-271, because `header` is still `True`). The result is `inp['My Table'] == {}` — a well-formed empty dict, no warning, no exception. The failure surfaces much later and far away as `KeyError: "Row 'X' in table 'My Table' is required but not found in dcf.inp"` (input_resolver.py:427) or as `Table 'X' is required but not found`. A second, worse variant: if the header/separator happen to be pipe-less but a *data* row has a leading pipe, `table_entries[0]` is `''`, so every such row is stored under the key `''` and each overwrites the last (line 275). For the UI this is the single most important parser fact: whatever emits the markdown must **not** emit leading or trailing pipes on the separator row. Suggested fix: strip a leading/trailing `|` from every line before dispatching, and detect the separator with `set(line.replace('|','').strip()) <= {'-',' ',':'}` rather than `line[0] == '-'`.

### CORE-2 — Missing blank line between tables reuses the previous table's columns
**BUG-confirmed-by-reading** · `input_modification.py:257-277` · known upstream? **NEW**

`table` is reset to `False` only by a blank line (line 262-263). The `#` branch (line 257-260) resets `header` but **not** `table`. So when a `# Next Table` header immediately follows a data row with no blank line in between, three things happen in one iteration: the new table dict is created (259), and then — because `table` is still `True` and `line[0] != '-'` — the header line itself is parsed as a data row, creating the junk row `inp['Next Table']['# Next Table'] = {}` (273-275). Worse, `header_entries` still holds the *previous* table's column names, so every subsequent row of the new table is stored under the old table's column names until a `---` line resets them. Since the new table's own header line is consumed as a data row rather than as a header, the columns stay wrong for the whole table. The junk row also trips `check_processing()` later ("has not been processed"), which is the only visible symptom. A UI generating input files must emit a blank line before every `#`.

### CORE-3 — `UnboundLocalError` when content precedes the first header
**BUG-confirmed-by-reading** · `input_modification.py:258, 271, 275` · known upstream? **NEW**

`variable_name` (258) and `header_entries` (271) are plain locals with no initialisation. If the file starts with a table row, or with a `---` line, or with any line whose first character is `-` before the first `#` header, line 275 raises `UnboundLocalError: local variable 'variable_name' referenced before assignment` (or `header_entries` at 277). For a non-programmer editing an input file that is the least actionable message the engine can emit — it names a Python local, not the offending line, and gives no line number. The fix is trivial (initialise to `None` and raise a message naming the file and line number), and it is the highest value/effort ratio item in this report for issue #141.

### CORE-4 — Duplicate names overwrite; ragged rows truncate
**BUG-confirmed-by-reading** · `input_modification.py:259, 275, 277` · known upstream? **NEW** (naming-consistency issues #83/#101/#173/#174 are about *choosing* names, not about collisions)

Three silent data-loss paths in the same loop. (a) Line 259 does `inp[variable_name] = {}` unconditionally, so a second `# Direct Capital Cost` header anywhere in the file — including one arriving from a merged defaults file that was concatenated by hand — wipes the first table. (b) Line 275 does the same at row level, so two rows with the same name in one table keep only the last. (c) Line 277 zips header cells against row cells, so a row with fewer cells than the header silently loses its trailing columns (typically `Unit`, which then makes the row resolve as a bare value rather than a `Quantity`), and a row with more cells silently loses the extras. Given that input files are hand-edited and merged, all three deserve a duplicate/arity check that raises with the table name.

### CORE-5 — Any line beginning with `-` is treated as a separator
**LIKELY-BUG** · `input_modification.py:266-268, 273` · known upstream? **NEW**

`if line[0] == '-'` (266) sets `table = True` and the line is then skipped by the guard at 273. This means a markdown bullet list used as a comment between tables (`- note: values from Chang 2020`) silently switches the parser into table mode, so every following non-blank line up to the next blank line is parsed as a data row of whichever table is currently open, using whatever `header_entries` was last seen. It also means a row whose *name* starts with a hyphen (`-40 degC case | …`) is silently dropped. Comments are already unsupported by the format, which makes this trap easy to fall into.

### CORE-6 — `num()` edge cases: crash, and silent numeric corruption
**BUG-confirmed-by-reading** · `input_modification.py:200-212` · known upstream? **NEW**

Three issues. (a) `s[-1]` on line 200 raises `IndexError: string index out of range` for an empty string; the parser guards this by mapping empty cells to `'n/a'` (line 280-281), but `num()` is public and is also reached from `process_cell` (749) and `parse_parameter_to_array`. A cell containing only `%` recurses to `num('')` and raises the same `IndexError`, which the `except TypeError` on line 202-203 does not catch. (b) `s.replace(',', '')` (207/210) removes *all* commas before parsing, so the European decimal `1,5` becomes the integer `15` and `1,00,000` becomes `100000` — a 10× error with no warning, in a project whose users are largely non-US. (c) `float()` accepts `nan`, `inf`, `-inf`, `Infinity`; a cell containing the word `inf` becomes a float infinity that propagates through the whole DCF and yields `nan` costs. Recommend: reject a string as numeric unless the comma grouping is well formed, and reject non-finite literals.

### CORE-7 — Empty cells and typos silently become the number 1
**USABILITY** · `input_modification.py:280-285` and `748-754` · known upstream? relates to **#141** (error-message comprehensibility), not otherwise tracked

An empty cell becomes the string `'n/a'` (281). When that row is later resolved, `process_cell` takes the `'>' not in cell` branch, `num('n/a')` returns a string, and the function prints `Warning: Value at "T > R > Value" is not numerical (value is "n/a"), setting to 1.` and returns `1.` (753-754). The same happens for any typo (`0.98 %` with a stray space is fine, but `O.98` with a capital O is not). Because the fallback is `1.` and not `0.` or an exception, the substitution is invisible in the output: a forgotten efficiency silently becomes 100 %, a forgotten cost multiplier silently becomes ×1. For a UI this is the strongest argument to surface captured stdout warnings as first-class validation errors — and for the engine, the strongest argument to make this fatal by default.

### CORE-8 — A path to an already-processed number silently resolves to 1
**BUG-confirmed-by-reading** · `input_modification.py:691-700` · known upstream? closest is **#97** (closed — ordering of paths vs `sum_all_tables`), but that issue is about resolution *order*; this is about the *type* stored at the target. Treat as **NEW**

`process_path` has two branches for the target value. If the target row has no `Processed` marker, it is converted to a `Quantity` (691-692). If it *does* have one, whatever is stored is used as-is — and only `Quantity` is accepted (694). Plugins insert plain `int`/`float`/`ndarray` values into `dcf.inp` in many places (any `insert()` whose value is not a `Quantity`), and `process_input` itself writes back a bare float at line 847. Any user path pointing at such a cell falls into the `else` at 697 and is replaced by `1.` — while printing `Warning: Non-numerical (non-Quantity) value retrieved … obtained value is 12345.0, setting to 1`, a message that literally contradicts itself by displaying the number it just called non-numerical. Because the outcome depends on which plugin ran first, the same input file can give different answers if `Position` values change. This is a correctness bug, not just a message bug: the levelized cost is wrong and nothing raises.

### CORE-9 — One `except KeyError` hides four different user mistakes
**BUG-confirmed-by-reading** · `input_modification.py:702-705` (with `618-645`) · known upstream? **NEW** (extends **#141**)

The `try` block at 687-700 spans four failure sources, and all of them print the identical `Warning: Invalid path specified for "{path}" (at "T > R > C"), setting to 1`: (1) a genuinely dangling path (wrong table/row/column name, or a case/spelling difference — all lookups are exact and case-sensitive); (2) `keys['Unit']` at line 642 — the target row exists but has **no `Unit` column**, which is the normal shape for e.g. `Display Parameters` or any single-value row, so pointing at a legitimate unit-less cell reports "invalid path"; (3) `bottom_keys[parsed_path[2]]` at line 630 — the path's bottom key is not a *value* key (e.g. it points at `Unit`, at `Path`, or at the unit half of a `X_Value`/`X_Unit` pair, which `identify_bottom_keys` absorbs and therefore does not return as a key); (4) any `KeyError` raised arbitrarily deep inside the recursive `process_input` call at 633-639, including one from a completely different table. Splitting these into distinct messages ((2) and (3) in particular should say "target row has no Unit column") would remove a large share of the troubleshooting time that #141 complains about.

### CORE-10 — Circular path references recurse until the stack dies
**LIKELY-BUG** · `input_modification.py:691-692` + `633-639` · known upstream? **NEW**

`create_quantity_from_user_input_and_insert` calls `process_input(..., add_processed=False)` (line 638), i.e. it deliberately does **not** mark the target as processed. So if `A > B > Value` contains `{C > D > Value, kg}` and `C > D > Value` contains `{A > B > Value, kg}`, the guard at 691 never becomes true for either row and the pair recurses until Python raises `RecursionError: maximum recursion depth exceeded`. The traceback is ~1000 frames of `process_input → process_cell → process_path` with no indication of which two cells are involved, and `input_resolver_function`'s wrapper (695-697) then tries to re-raise it via `type(error)(...)` on a possibly empty `args` (see CORE-23). A visited-set carried through the recursion would both terminate and name the cycle.

### CORE-11 — The unit in `{path, unit}` is not reconciled with the row's own `Unit`
**BUG-confirmed-by-reading** · `input_modification.py:678, 695` + `IO/input_resolver.py:347-370` · known upstream? extends **#108** (closed: "clarify the behaviour of variable references") — the semantics were documented, this specific hazard was not. Treat as **NEW**

`process_path` returns a bare float expressed in the unit written inside the braces (695: `target_value.unit[unit]`). The row's own `Unit` cell is then applied independently by `value_with_unit_resolver_function`, which builds `Quantity(value_retrieved, unit_retrieved)` from the *row's* unit (input_resolver.py:363-370). Nothing checks that the two agree. Writing `Value = {Electrolyzer > Energy > Value, kWh}` in a row whose `Unit` column says `MJ` produces a quantity that is wrong by a factor of 3.6, and every downstream check passes because the *dimension* is right (energy). The mistake is easy to make precisely because the braces syntax invites you to write a unit there. Either the path unit should be ignored in favour of the row unit, or the resolver should compare them and raise. A UI that offers a path-picker should auto-fill both from the same source.

### CORE-12 — Legacy brace-less paths raise an unlocated `ValueError`; the shipped `data/` examples all use them
**USABILITY** · `input_modification.py:479-483` · known upstream? **NEW**

`parse_path_with_unit` raises `ValueError: Expected a string wrapped in braces, but got 'Hourly Irradiation > Latitude > Value' instead` (480) — with no table/row/column of the *offending* cell, because it does not receive them. A brace-wrapped path missing the comma (`{A > B > Value}`) fails differently and worse, at line 483: `ValueError: not enough values to unpack (expected 2, got 1)`. Both are user-facing: every input file under `pyH2A/data/**` (e.g. `data/PV_E/Base/PV_E_Base.md:31`, `:41`) is still in the pre-brace format and will hit the first error; `data/pyH2A_execution.py:20` points at exactly that file. Either those examples should be migrated or removed, since a new user following the README lands on them first. Passing `top_key/key/bottom_key` into `parse_path_with_unit` for the message is a two-line change.

### CORE-13 — Wrong or unknown unit in a path escapes with no location
**USABILITY** · `input_modification.py:695` (raising from `Unit_Handler/quantity.py:139-150, 60-61`) · known upstream? **NEW** (extends **#141**)

`target_value.unit[unit]` raises `ValueError: Dimension mismatch: original dimension 'currency', but requested dimension 'mass' when mapping 'kg'` for a wrong unit, or `ValueError: Unknown unit encountered during parsing: 'hour'` for a typo. Neither is a `KeyError`, so the guard at 702 does not catch them (correctly — they should be fatal), but neither message contains the table/row/column of the cell that wrote the path, and `process_path` does not wrap them. The user sees a dimension pair and has to grep their input file for the unit string. Wrapping lines 694-695 in a `try/except ValueError` that re-raises with `"{top_key} > {key} > {bottom_key}"` prefixed would fix it.

### CORE-14 — `dcf.inp` is mutated in place and the constructor does not copy
**BUG-confirmed-by-reading / UI-FACT** · `Discounted_Cash_Flow.py:194-197` · known upstream? **NEW**

`__init__` parses the file when given a `str`, but when given a `dict` it stores the caller's object directly (197). The run then mutates it extensively: `process_input` replaces cell contents with computed values and stashes the original under `'Former ' + bottom_key` (844-847), sets `Processed` (463 in input_resolver), `value_with_unit_resolver_function` overwrites numeric cells with `Quantity` objects (input_resolver.py:369-378), and plugins insert whole new rows and tables (`Summed Total`, `Summed group total`, `Contributions`, `Dependent Variables`). Consequences a UI must handle: (1) **a second `Discounted_Cash_Flow(inp)` on the same dict is not a re-run** — every row short-circuits on `Processed` at input_modification.py:817-819, so plugin inputs come back as the *previous* run's outputs rather than the user's edits; (2) the inserted sum rows change the results of the second run outright (CORE-16); (3) anything the UI displays from `inp` after a run is a mixture of `Quantity` objects, floats, ndarrays and dicts, not the strings the user typed — the user's original text survives only in `Former Value`. The existing callers get away with it by deep-copying per evaluation (`Discounted_Cash_Flow.py:58`, `:97`, `Monte_Carlo_Analysis.py:310`). The engine should `copy.deepcopy` at line 197 (or the UI must, on every single run).

### CORE-15 — `Processed` is a row flag but processing is per column
**LIKELY-BUG** · `input_modification.py:817-819`, `459-460`, `IO/input_resolver.py:462-463` · known upstream? **NEW**

`process_input` returns the raw cell unchanged the moment `'Processed'` is present anywhere in the row (817-819), and `insert()` stamps `Processed` on the whole row after writing a single bottom key (459-460), as does `row_resolver_function` (463). Rows routinely have several independent values (`Usage_Value`/`Usage_Unit`/`Usage_Path` plus `Cost_Value`/`Cost_Unit`/`Cost_Path` — see `Variable_Operating_Cost_Plugin.py:170-182`). So if plugin A inserts one output into a row that also holds a user-supplied, path-bearing sibling value, the sibling is frozen: when plugin B later resolves it, `process_input` hands back the raw path string, its `Path` multiplier is never applied, and the user gets `TypeError: 'T > R > Cost_Value' (entry: '{X > Y > Value, USD}'): Expected (<class 'int'>, <class 'float'>), but got <class 'str'>` from `check_type` — an error that describes a type mismatch when the actual fault is a premature `Processed` stamp. The marker should be per bottom key (e.g. `Processed Cost_Value`) or the row flag should be a set of processed keys.

### CORE-16 — Sum rows are re-consumed by wildcard resolution → double counting, then `TypeError`
**LIKELY-BUG** · `IO/input_resolver.py:490-492`, `560-579`, `605-615` · known upstream? related to **#102** (closed: sums vs missing tables) and **#97** (closed: ordering); the re-entrancy angle is **NEW**

`sum_table_quantity(..., insert_total=True)` writes a `Summed total` row back into `dcf.inp[top_key]` (input_modification.py:944-946), and `sum_all_tables_quantity` writes a whole `Contributions` row plus a group-total table named exactly the group prefix (1023-1027). Both are then visible to any *subsequent* resolution: `wildcard_row_resolver_function` iterates `dcf_class.inp[top_key]` unconditionally (490), and `table_group_resolver_function` selects tables by `if table_group_top_key in key` (611), which matches the inserted group table itself. Within a single run this is latent (each group is resolved once); it becomes real (a) if two plugins declare the same wildcard group, and (b) always on a second run against the same dict (CORE-14). The failure is not clean: the `Summed total` row resolves fine and gets added to the new total (silent double counting), while the `Contributions` row holds a dict containing the string `'Table Group'`, which `_create_quantity_and_validate` rejects at input_resolver.py:205-209 with `TypeError: 'Direct Capital Cost > Contributions > Value': Unsupported type '<class 'str'>' when trying to resolve quantity value.` Either the inserted rows need a marker that wildcard resolution skips, or the sums should live outside `inp`.

### CORE-17 — `insert()` clobbers the row's `Path` cell
**SMELL** · `input_modification.py:435-437` · known upstream? related to **#68** (closed, "Path bottom key can't be optional") — different mechanism, **NEW**

Every `insert()` with `insert_path=True` (the default, and the default used by `output_inserter.insert_value` at 218-219) writes the string `'None'` into `inp[top][middle]['Path']`. If the row already carried a user path for a *different* bottom key that has not been resolved yet, that multiplier is destroyed. In practice the row is also stamped `Processed` on the same call, so the value never gets re-derived and the loss is invisible. It also fabricates a `Path` column in rows that never had one, which pollutes anything that iterates the row's bottom keys (`identify_bottom_keys` will attach it as the `Path` of the bare `Value` pair, line 586-587). Prefixed paths (`Cost_Path`) are untouched, which makes the behaviour inconsistent between the two supported row shapes.

### CORE-18 — Output silently skipped when a plugin attribute is `None`
**BUG-confirmed-by-reading** · `IO/output_inserter.py:223-232` · known upstream? **NEW** (mechanically adjacent to **#116**)

`_retrieve_value_to_be_inserted` returns `None` for two very different situations: the attribute is missing *and* the row is declared optional (72-74), or the attribute exists and its value happens to be `None`. `insert_value` then does `if value_to_be_inserted is None: return` (231-232) without distinguishing them, so a plugin that initialises `self.x = None` and fails to compute it produces no output, no warning and no error — even for a row explicitly marked `'optional': False`. The consumer of that output fails later with `KeyError: "Key 'Value' not found in dcf.inp at location 'T > R > Value'"` naming a completely different plugin. A sentinel (or checking `optional` at the point of the `None` return) makes the non-optional case fatal where it belongs.

### CORE-19 — What the output checks actually cover (and don't)
**LIKELY-BUG** · `IO/output_inserter.py:120-173`, `check_functions.py:44-62` · known upstream? extends **#116** (open) — that issue's root cause is stated as "this variable is not subject to the output_dict checks"

Mapping the validation surface, because a UI will want to know which garbage can reach `inp`: for a top-level `Quantity`, `check_type` on `base_value` + `check_dimension` run (156-168); for a top-level `str`, only `check_type` (141-148); for a `dict`, `check_type` on the dict itself, then recursion with `check_type_setting=False` (122-137) — so **every leaf inside a dict skips `check_type` entirely**, and a `str` leaf skips both checks (a wrong-unit or wrong-typed entry buried in a contributions/`yearly_data` dict passes untouched, which is exactly the escape route #116 describes); numeric leaves inside a dict raise `TypeError` from the `else` at 170-173. And across the board **`check_bounds` is never called on outputs** — it exists (`check_functions.py:44-62`) and is wired only into the input path (`input_resolver.py:110-116`) — so a plugin can emit a negative cost or a >100 % efficiency and nothing notices. Finally the recursion reuses the same `value_dict` for every leaf, so a heterogeneous dict output (mixed dimensions) is inexpressible.

### CORE-20 — `PATH_KEY` means two different things in the two spec dialects
**API-inconsistency** · `Utilities/constants.py:31` vs `IO/output_inserter.py:6-20` · known upstream? **NEW**

`constants.PATH_KEY = 'path'` and is read from the **value**-level spec by `input_resolver.value_resolver_function` (248). `output_inserter.PATH_KEY = 'path_key'` (line 9) and is read from the **row**-level spec (219). `output_inserter` also re-declares `OPTIONAL_KEY`, `TYPE_KEY` and `DIMENSION_KEY` locally instead of importing `constants`, so the two files can drift silently — as `PATH_KEY` already has. ### CORE-21 — A table with `sum_tables` can never be optional
**SMELL** · `IO/input_resolver.py:525` · known upstream? related to **#102** (closed), **NEW** in this form

`is_required = any(not row_dict.get(OPTIONAL_KEY, False) for row_dict in table_dict.values())` iterates *all* values of the table spec, including the `sum_tables` pseudo-row `{'mode': ..., 'arguments': {...}}`, which has no `optional` key and therefore contributes `True`. So any table carrying a `sum_tables` block is treated as required even when every real row is optional, and a user who omits the whole table gets `KeyError: "Table 'X' is required but not found in dcf.inp"`. ### CORE-22 — Group membership by substring; sum arguments plumbed by `pop()`
**SMELL** · `IO/input_resolver.py:608-624`, `input_modification.py:1008-1013` · known upstream? naming fragility overlaps **#101**/**#83**

A table belongs to a group if the group name is a *substring* of the table name (611, and again at input_modification.py:1010). `'Other Direct Capital Cost'` would silently join the `'Direct Capital Cost'` group; so would a table a user names `'Notes on Direct Capital Cost'`. ### CORE-23 — `raise type(error)(msg)` is an unsafe re-raise idiom
**LIKELY-BUG** · `IO/input_resolver.py:695-697`, `IO/output_inserter.py:309-311` · known upstream? **NEW** (contributes to **#141**)

Both top-level wrappers do `raise type(error)(f"[Plugin: {name}] {msg}") from error`. This assumes every exception type can be reconstructed from a single string. It cannot: `UnicodeDecodeError` needs five arguments, `OSError` carries `errno`, and any plugin-defined exception with a custom `__init__` breaks — in which case the user sees a `TypeError` raised *during* handling and the real error only in the chained traceback. It also mangles `KeyError`, whose `str()` re-adds quotes, so a carefully worded message like `Row 'x' in table 'y' is required…` is displayed as `"[Plugin: P] Row 'x' in table 'y' is required…"` — quoted, which reads like a stray string. And `error.args[0]` (696) may be a non-string (e.g. `KeyError` raised with a tuple). Idiomatic fix: `error.add_note(f"[Plugin: {name}]")` (3.11+) or re-raise a single dedicated `PluginError` type.

### CORE-28 — Diagnostics are `print`-only
**UI-FACT** · `Discounted_Cash_Flow.py:236-239`; also `input_modification.py:682, 698, 703, 710, 753` · known upstream? **NEW**

Every non-fatal diagnostic in the engine is a bare `print()`: unprocessed tables (239), invalid paths, non-numerical values, `insert()` overwrite notices (438-443). None of them is recorded on the `Discounted_Cash_Flow` object, and `check_processing` returns `None`. ### CORE-29 — Filesystem read surface, and two `importlib.resources` hazards
**UI-FACT / SMELL** · `input_modification.py:115-155`, `368-375` · known upstream? **NEW**

All engine reads funnel through `file_import`. Two modes: a path containing `~` is resolved as `package~filename` against the installed package (`pyH2A.Lookup_Tables~MACRS.csv`, `pyH2A.Config~Defaults_TEA.md`), anything else is `open(Path(file_name))` — i.e. **relative to the process CWD, not to the directory of the input file that referenced it** (368-375). A `Input files to merge` row pointing at `src/tests/end_to_end/foo.md` only works if the process was started from the repo root; in a browser/stlite port every such path must be made absolute or the working directory pinned. Three further defects in the same function: (i) `file_name.split('~')` (137) raises `ValueError: too many values to unpack` if the name contains two tildes; (ii) `return_path=True` opens the file at 139-142 and then returns only the path, leaking the handle — and no caller anywhere in the repo passes `return_path`, so the whole branch is dead weight; (iii) line 143-144 uses `with importlib.resources.path(package, file) as path: output_path = path` and then uses `path` **after** the context manager has exited — for a non-filesystem loader (zipimport, and relevant for any WASM bundling that does not unpack the wheel) that temp file is deleted at exit, so the returned path may not exist. `open_text`/`open_binary`/`path` are the legacy functional API: deprecated in 3.11-3.12, briefly removed in the 3.13 alphas and then restored/un-deprecated (CPython gh-116608), so they work today but emit `DeprecationWarning` on 3.11/3.12 and are the wrong API for a resource loader that may not be a real filesystem. `files(package).joinpath(name).open(...)` is the portable form.

### CORE-30 — `read_textfile` caches unbounded, shared, mutable arrays
**SMELL** · `input_modification.py:157-178` · known upstream? extends **#152** (open — `lru_cache` leak on `Hourly_Irradiation_Plugin`); this is a second, independent instance

`@lru_cache(maxsize=None)` on a function returning an `ndarray` means (a) every distinct `(file_name, delimiter, mode)` tuple is retained for the process lifetime — for the hourly-irradiation TMY files that is tens of MB per location, which matters in a browser sandbox — and (b) **every caller receives the same array object**. `Discounted_Cash_Flow_Plugin.py:52-55` already defends against this (`macrs = np.copy(original_macrs)` before scaling by 100), which is evidence the trap has been hit at least once; `Photovoltaic_Plugin.py:188` takes a view (`[:,1]`) and would corrupt the cache if it ever wrote through it. Returning `data.copy()` (or a read-only view via `data.setflags(write=False)`) removes the sharp edge; `maxsize` should be finite.

### CORE-32 — `find_nearest` clamps out-of-range lookups silently
**SMELL** · `Utilities/find_nearest.py:23-36` · known upstream? **NEW**

`np.searchsorted` assumes a sorted array (only the first column is used when 2-D, lines 22-25) and there is no check. **SMELL** · `Utilities/docstring_generation.py` (whole file), vs `plugin_input_output_processing.py:6-12, 41` · known upstream? **NEW**

`generate_docstring` has **zero callers** — grep for `generate_docstring|__doc__` finds only its own definition and its module docstring's usage example. ## Cross-cutting notes for the UI agent

1. **Deep-copy the input dict before every run** (CORE-14). `Discounted_Cash_Flow(path_str)` re-parses and is safe; `Discounted_Cash_Flow(dict)` is not.
2. **Capture stdout** — it is the only channel for "your path was invalid and I used 1 instead" (CORE-7/8/9/28).
3. **Generate markdown without leading/trailing pipes, with a blank line before every `#`, with `---` separators, and never with a row name starting with `-`** (CORE-1/2/5).
4. **Numbers**: decimal point only, `%` suffix allowed, commas are stripped as thousands separators (so never emit a comma decimal) (CORE-6).
5. **After a run, cell values are `Quantity`/ndarray/dict, not the user's strings**; the original text is under `Former <key>`. The levelized cost is at `inp['Dependent Variables']['Levelized cost']['Value']` and the breakdown at `['Levelized cost contributions']['Value']` (a dict with `Data`/`Total`/`Table Group`).
6. **Mandatory tables**: `Functional Unit` (row `Functional Unit`, column `Unit`) and `Workflow` (column `Position`, row name = plugin module name). `Input files to merge` is optional; its `Value` cells are CWD-relative paths or `package~file` references (CORE-27/29).
7. **Nothing is written to disk by the engine** (CORE-31); read-only VFS is sufficient for cost calculation.
